# Spike report — true peak: end-to-end cost of a fourth PCM read, and the stop rule

> **What this is.** Group 5 of change `add-true-peak-measurement`. It measures what a *whole
> inspection* costs with three sample-reading operations versus four, against the real decode path,
> and applies the stop rule `design.md` §8 wrote in advance.
>
> **What it is not.** Not a benchmark suite, not a claim about any machine but this one, and not a
> redesign. It measures and decides; it changes no production code.

- **Date prepared**: 2026-08-12
- **Branch**: `design/add-true-peak-measurement`
- **Harness**: temporary, in the test target, **created, measured and deleted** — never committed. It
  drove the real `SourceInspectionCoordinator` with its production defaults, real files on disk, real
  AVFoundation decode, and the real `TruePeakAccumulator` composed exactly as
  `SignalLevelMetricsGeneration` composes its own operation.
- **Related**: `design.md` §8 (the stop rule) and §9, ADR-0016 (independent operations; deduplication
  permitted *on top of* the seam once measurement justifies it), ADR-0019 (`Proposed`), and the
  methodology spike of 2026-08-11.

## The question

Not "what does the DSP cost" — group 4 answered that (0.57 s Release / 1.06 s Debug for ten minutes of
stereo). The question is what a **fourth read of the file** costs beside an inspection that already
performs three, because that is the cost a PCM-sharing change could remove and the one the stop rule
governs.

## Method

For each fixture, in each build configuration:

1. **baseline** — one full `SourceInspectionCoordinator.inspect`: report, waveform, spectrogram, signal
   level metrics (three sample reads).
2. **with true peak** — the same inspection followed by the true-peak operation (four sample reads).
3. **true peak only** — the true-peak operation alone: decode + `PCMChunk` construction + accumulation.
4. **decode only** — the same decode with a no-op receive, isolating what *reading the file again*
   costs with nothing computed on it.
5. **time to report** — how long until the coordinator emits `.report`.

Each figure is the **minimum of three runs** after one warm-up pass, on an otherwise idle machine.
Minimum rather than mean, because the noise here is all additive.

## What the numbers say

### The decode is not free, and for compressed formats it is most of the added cost

For a ten-minute stereo file the fourth read alone costs:

| | decode only | share of the baseline inspection |
| --- | --- | --- |
| WAV, Release | 0.051 s | **7.0 %** |
| WAV, Debug | 0.619 s | **16.3 %** |
| FLAC, Release | 0.473 s | **23.5 %** |
| AAC, Release | 0.534 s | **23.6 %** |
| FLAC, Debug | 1.042 s | **20.5 %** |

**The compressed rows are the ones that matter.** This product exists to examine whether a "lossless"
file really is lossless, so FLAC, ALAC, AAC and MP3 are its subject, not the uncompressed case where
decode is nearly free. For those, reading the file a fourth time — computing nothing — costs about a
**quarter of the whole inspection**.

The same measurement says something about the *existing* three reads: a FLAC baseline of 2.011 s in
Release contains roughly 1.42 s of decoding the same file three times. Deduplication is therefore
worth more than this change alone would gain from it.

### The design's premise was wrong by more than an order of magnitude

`design.md` §8 accepted the fourth read partly on a cited figure: *"the fourth decode itself costs
**0.035 s** (the figure already measured for a ten-minute stereo file)"*, taken from
`SignalLevelMetricsAccumulator`'s own documentation. Measured here against the real port — including
the `PCMChunk` construction and finiteness screen every consumer of the seam pays — the same read costs
**0.051 s for WAV in Release** (close to the cited figure) but **0.473–0.534 s for a compressed file**,
and **0.619–1.042 s in Debug**. The cited number described the cheapest possible case and was carried
into a decision about the general one.

This is exactly the escape hatch §8 kept open: *"remains the escape hatch if group 5's numbers against
the real decode path disagree."* They disagree.

### The true-peak DSP is a separate cost that deduplication cannot touch

Subtracting decode from the true-peak operation leaves the measurement itself: about **0.51 s in
Release and 0.53 s in Debug** for ten minutes of stereo. No amount of PCM sharing removes it — it is
what measuring a true peak costs, and it is the price of the feature rather than of the architecture.

Stating both halves separately matters, because they have different remedies and only one of them is
what the stop rule is about.

### No contention, no anomaly

In every row the delta equals the isolated operation almost exactly — 0.064 against 0.061, 1.152
against 1.152, 0.560 against 0.557. **The total is the sum.** Nothing appears from cache pressure,
AVFoundation setup, the security scope or allocation churn: a fourth operation costs what it costs on
its own and nothing extra for being fourth.

### The report is never delayed

Time to the `.report` update was **0.001–0.002 s** in every fixture and both configurations. The
coordinator emits the report before any sample read begins, so a fourth operation appended after the
existing three cannot delay the report, the waveform, the spectrogram or the signal level metrics.
Whatever group 6 does, it must keep that order — and the order it plans to use already does.

### Memory

Checked structurally rather than by RSS, which is the honest way to answer it:

- `TruePeakAccumulator` retains `pending` capped at `tapsPerPhase - 1` per channel, plus one `peak` and
  one `sampleCount` per channel — `O(channelCount × tapsPerPhase)`.
- `window` and `convolved` are sized to the largest chunk seen and reused, never to the file.
- The 384 coefficients are built once per operation.
- **The 8× oversampled signal is never materialised** — no buffer of `8 × outputCount` exists.
- The decoder hands each chunk to `receive` and retains nothing.

No accidental buffering.

## Comparison with the earlier spikes

| | 10 min stereo, Release | 10 min stereo, Debug |
| --- | --- | --- |
| Methodology spike, DSP only (48t/8×, vDSP) | 0.693 s | 5.24 s |
| Group 4, production DSP over synthetic buffers | 0.570 s | 1.057 s |
| **Group 5, real path (decode + chunk + accumulate)** | **0.557 s** | **1.152 s** |

Same order of magnitude throughout, and every difference is accounted for:

- The **spike's Debug figure is ~5× the production one** because it converted `Double` → `Float` per
  chunk and allocated per call; production keeps `Float` natively and reuses buffers. The spike report
  flagged this as a caveat at the time.
- The **real path is marginally faster than group 4's synthetic measurement in Release** because that
  harness built a `PCMChunk` from freshly sliced arrays on every chunk — an allocation and a finiteness
  screen over new storage that the real decoder does not repeat.

No difference above 2× is unexplained.

## The stop rule, applied

The rule, quoted from `tasks.md` 5.3 and `design.md` §8 rather than restated:

> *"if the fourth decode is not clearly insignificant beside the rest of an inspection, **do not** fold
> operations together inside this change — record the number and open a separate deduplication change,
> as ADR-0016 provides for."*

**The fourth decode is 23.5 % of a FLAC inspection and 23.6 % of an AAC one in Release, and 16–21 % in
Debug.** That is not clearly insignificant by any reading of the phrase.

### Verdict: the stop rule is triggered

- **Nothing is folded, merged, migrated or redesigned here.** No operations are combined, the waveform
  is not migrated, the decoder is untouched, and no production file changed in this group.
- **The number is recorded** — this document.
- **A separate PCM-sharing change is the next step**, exactly as ADR-0016 anticipated: *"A single shared
  pass producing several results was considered and rejected in ADR-0016; if measurement ever justifies
  one, it can be built on top of this port rather than by changing it."* This is that measurement.
- **Group 6 is blocked** until that change lands. Adding a fourth independent read now would ship a
  ~24 % regression on the app's core formats with the intention of removing it later, which is a worse
  position than doing the sharing first.

### What the verdict does *not* say

- It does not overturn the fourth-operation *shape*. ADR-0016's independent-operation rule stands;
  the objection is to a fourth **read**, not to a fourth consumer. A sharing seam that feeds N
  accumulators from one pass preserves independent cancellation and independent failure, which is what
  ADR-0016 actually protects.
- It does not question the true-peak measurement, its methodology, its model or its accumulator. Those
  are done, tested and unaffected — the DSP cost is real but is the feature's own price, not the
  architecture's.
- It does not promote or demote ADR-0019, which is about what a true peak *is* and how it is reported.

## Limits of this measurement

- **One machine, one SDK, one run of each configuration set.** Minimum-of-three reduces noise but does
  not make these numbers portable.
- **44.1 kHz only.** Higher rates scale the sample count and would make every figure larger in the same
  proportion; nothing here suggests the ratios change.
- **MP3 is absent**, because the fixture writer cannot produce one natively (a documented gap). FLAC and
  AAC stand in for the compressed case, and both agree closely.
- **The coordinator is driven directly**, not through the app's UI, so nothing here measures rendering
  or the main-actor hop that a real interaction adds.
- **Discarded runs**: the first pass of every fixture was a warm-up and is excluded, so no figure above
  includes cold file-cache I/O.
